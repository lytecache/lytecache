Your first cache

About ten minutes, one script. You'll cache a slow HTTP call, share the cache between two processes, and look at the result from a shell. The tutorial uses Python. The other four languages work the same way, and every reference group shows their method names on the toggle.

  1. Install it and store one value

    Run pip install lytecache, then try the smallest program that does something:

    Python 
    from lytecache import LyteCache

cache = LyteCache()
cache.set("greeting", "hello")
print(cache.get("greeting"))

    It prints hello. You didn't start a server or choose a file. The first write created the file, and step 5 shows you where it is.

  2. Make a slow call twice

    Save this as slow_api.py. httpbin.org/delay/1 waits a second before it answers, standing in for any slow or rate-limited API.

    slow_api.py 
    import json
import time
import urllib.request

from lytecache import LyteCache

cache = LyteCache()
URL = "https://httpbin.org/delay/1"   # waits one second on purpose


def fetch(url):
    key = f"http:{url}"
    cached = cache.get(key)
    if cached is not None:
        return cached
    with urllib.request.urlopen(url) as resp:
        data = json.load(resp)
    cache.set(key, data)
    return data


for attempt in (1, 2):
    start = time.perf_counter()
    fetch(URL)
    print(f"call {attempt}: {(time.perf_counter() - start) * 1000:.2f} ms")
    Terminal 
    $ python slow_api.py
call 1: 1399.60 ms
call 2: 0.10 ms

    The first call went over the network and took 1.4 seconds. The second came from the cache in a tenth of a millisecond: one SQLite read from a file on your disk. Your numbers will differ. The gap won't.

  3. Give the data an expiry

    Right now the response is cached forever. Change the set line to give it a TTL:

    slow_api.py 
        cache.set(key, data, ttl=300)   # seconds

    Choose the number by asking how stale an answer you can live with. An exchange-rate feed that updates every few minutes is fine at 300 seconds. A user's own profile, which they expect to change the moment they edit it, shouldn't wait for a TTL at all: delete it when it changes (see Invalidate on write). The unit is seconds, so ttl=300000 would be 83 hours.

    Run the script now and both calls still hit the cache. The entry from step 2 was written without a TTL, and fetch() only writes on a miss, so your change hasn't touched it. A new TTL only applies to entries written after the change, which is worth remembering in production too. Clear the cache once and run it again:

    Terminal 
    $ python -c "from lytecache import LyteCache; LyteCache().flush()"
$ python slow_api.py
call 1: 1471.90 ms
call 2: 0.10 ms

  4. Run it from a second process

    Run the script again from the same directory, or from a second terminal:

    Terminal 
    $ python slow_api.py
call 1: 0.04 ms
call 2: 0.02 ms

    Both calls were hits. This is a brand-new process with nothing in memory, and it found the entry the last run wrote. This is where lytecache stops looking like a dictionary. The cache lives in a file, so every process that opens it shares it, and it survives restarts. A Node.js or Go program started from the same directory would read the same entry.

  5. Look at it from the shell

    Install the CLI (brew install lytecache/tap/lytecache; other platforms are in Install) and run it from the same directory:

    Terminal 
    $ lytecache which
/Users/you/Library/Caches/lytecache/fb0e4baed14c.db
(exists)
$ lytecache keys --long
KEY                               TYPE  TTL    SIZE
http:https://httpbin.org/delay/1  json  299.5  261
$ lytecache get 'http:https://httpbin.org/delay/1'
{
  "args": {},
  "data": "",
  ...

    which shows the file your script created. Its name comes from the directory you ran in, so the CLI finds it with no flags as long as you run it from the same place. keys --long shows the key, its type (json, because the response was a dict), the seconds left on its TTL, and its size. Seeing the row is usually what makes the model click: it's data in a file, and anything that can open the file can read it.

  6. What to read next

    The recipes cover what you'll want next: caching API calls with memoize, avoiding a stampede when a hot key expires, and idempotency keys. If something doesn't behave the way this tutorial did, start with Troubleshooting.

Where is my data?

Every implementation picks the same default file for the same project. Start a Python script and a Go service from the same directory and they share one cache, with nothing to configure.

<platform cache dir>/lytecache/<project-id>.db
Platform Default location
Linux $XDG_CACHE_HOME/lytecache/<project-id>.db, or ~/.cache/lytecache/<project-id>.db
macOS ~/Library/Caches/lytecache/<project-id>.db
Windows %LOCALAPPDATA%\lytecache\<project-id>.db

<project-id> is the first 12 hex characters of the SHA-256 hash of your working directory's resolved absolute path. Every implementation derives it the same way, so a Python script and a Java service started from the same directory land on the same file. Nothing is written into your repo. (The glossary explains SHA-256.)

Overriding it

  • Pass an explicit path: LyteCache("/data/cache.db") in Python, .path(Path.of("/data/cache.db")) on the Java builder, new LyteCache({ path: "/data/cache.db" }) in Node.js, lytecache.WithPath("/data/cache.db") in Go, new LyteCache(path: "/data/cache.db") in PHP.
  • Set LYTECACHE_PATH=/data/cache.db in the environment. It overrides the default in every language.

To find out which file a cache is using, ask it: LyteCache.default_path() / cache.path in Python, LyteCache.defaultPath() / cache.path() in Java, LyteCache.defaultPath() / cache.path in Node.js, lytecache.DefaultPath() / cache.Path() in Go, LyteCache::defaultPath() / $cache->path() in PHP. From a shell, lytecache which prints the path and whether the file exists.

Laravel is the one exception. Its cache driver defaults to storage_path('framework/cache/lytecache.db'), because that's where a Laravel app keeps its cache files. Change it with stores.lytecache.path in config/cache.php.

When to use lytecache

✓ Good fit

  • Single-node apps (or single-machine, multi-process apps) that want caching, counters, or TTLs with zero infrastructure
  • Scripts, CLIs, notebooks, small web services, background jobs, test fixtures
  • A cache that survives process restarts without a separate daemon
  • Multi-process coordination via the process-safe distributed lock
  • Mixed-language systems, where Python, Java, Node.js, Go and PHP processes share one cache file
  • Laravel apps that want Cache::remember() and Cache::lock() without running Redis. Switching the driver is one config line.

✕ Not a good fit

  • A cache shared live across several servers. SQLite is a local file, not a network service, so use Redis or Memcached.
  • Heavy write traffic from many processes. SQLite allows one writer at a time, so writes queue up and become the bottleneck.
  • Pub/sub across machines, streams with consumer groups, sorted sets, or other Redis data structures beyond key-value, counters and hashes. (Events between processes on one host do work; see Local events.)
  • Complex queries over cached data. Use a real database.

Cache an API or HTTP response

Use read-through caching when an upstream answer is slow, rate-limited or billed per call, and a slightly old answer is acceptable. memoize checks the cache, calls your function on a miss, and stores what it returns.

Set the TTL from how fast the data really changes, not from how often you call it. Exchange rates that update every few minutes can live for five minutes. A product catalogue edited twice a day can live for an hour.

@cache.memoize(ttl=300)             # rates update every few minutes
def exchange_rates(base):
    resp = requests.get(f"https://api.example.com/rates?base={base}", timeout=5)
    resp.raise_for_status()         # an exception is never cached
    return resp.json()

exchange_rates("USD")   # network
exchange_rates("USD")   # cache, for the next 300 seconds
Rates rates = cache.memoize("rates:" + base, Duration.ofMinutes(5),
    () -> ratesClient.fetch(base));    // an exception is never cached
// memoizeAsync for a loader that returns a Promise
const rates = await cache.memoizeAsync(`rates:${base}`, 300, async () => {
  const resp = await fetch(`https://api.example.com/rates?base=${base}`);
  if (!resp.ok) throw new Error(`rates: HTTP ${resp.status}`); // never cached
  return resp.json();
});
rates, err := lytecache.Memoize(cache, "rates:"+base, 5*time.Minute,
    func() (Rates, error) {
        return ratesClient.Fetch(base) // a non-nil error is never cached
    })
$rates = $cache->remember("rates:{$base}", 300, function () use ($http, $base) {
    return $http->get("https://api.example.com/rates", ["base" => $base])
        ->throw()                       // an exception is never cached
        ->json();
});

Caveat. Whatever your function returns is cached for the full TTL, including a 200 response that contains an error message. Check the response before you return it, as the examples do. memoize also doesn't protect against a stampede when a popular key expires; the next recipe does.

Avoid a cache stampede

When a hot key expires, every request that arrives before it's rebuilt misses at once, and they all hit the slow backend together. If the rebuild is expensive, that pile-up can take the backend down.

Take a lock around the rebuild, then check the cache again once you hold it. The first request rebuilds. The others wait, find the fresh value on their second check, and never touch the backend.

def get_report(day):
    key = f"report:{day}"
    report = cache.get(key)
    if report is not None:
        return report
    with cache.lock(f"rebuild:{key}", timeout=30):
        report = cache.get(key)          # rebuilt while we waited?
        if report is None:
            report = build_report(day)   # the slow part
            cache.set(key, report, ttl=600)
    return report
Report getReport(String day) {
    String key = "report:" + day;
    Report report = cache.get(key, Report.class);
    if (report != null) return report;
    try (CacheLock lock = cache.lock("rebuild:" + key, Duration.ofSeconds(30))) {
        report = cache.get(key, Report.class);   // rebuilt while we waited?
        if (report == null) {
            report = buildReport(day);           // the slow part
            cache.set(key, report, Duration.ofMinutes(10));
        }
    }
    return report;
}
function getReport(day: string): Report {
  const key = `report:${day}`;
  let report = cache.get<Report>(key);
  if (report !== undefined) return report;
  using lock = cache.lock(`rebuild:${key}`, { timeoutMs: 30_000 });
  report = cache.get<Report>(key);         // rebuilt while we waited?
  if (report === undefined) {
    report = buildReport(day);             // the slow part
    cache.set(key, report, { ttl: 600 });
  }
  return report;
}
func getReport(day string) (Report, error) {
    key := "report:" + day
    var r Report
    if found, err := cache.Get(key, &r); err != nil || found {
        return r, err
    }
    lock, err := cache.Lock("rebuild:"+key, 30*time.Second)
    if err != nil {
        return r, err // lytecache.ErrLockTimeout if a rebuild takes too long
    }
    defer lock.Release()
    if found, err := cache.Get(key, &r); err != nil || found { // rebuilt while we waited?
        return r, err
    }
    if r, err = buildReport(day); err != nil { // the slow part
        return r, err
    }
    return r, cache.Set(key, r, lytecache.TTL(10*time.Minute))
}
function getReport(LyteCache $cache, string $day): array
{
    $key = "report:{$day}";
    $report = $cache->get($key);
    if ($report !== null) {
        return $report;
    }
    return $cache->lock("rebuild:{$key}", timeout: 30.0)->block(function () use ($cache, $key, $day) {
        $report = $cache->get($key);          // rebuilt while we waited?
        if ($report === null) {
            $report = buildReport($day);      // the slow part
            $cache->set($key, $report, ttl: 600);
        }
        return $report;
    });
}

Caveat. Waiting requests block for up to the lock timeout, and that timeout is also the lock's TTL. If a rebuild takes longer than the timeout, the lock expires and a second worker starts rebuilding too. Set the timeout well above your slowest rebuild. The lock only coordinates processes on this host.

Serve stale data when an upstream is down

Keep two copies of the answer: a short-lived "fresh" one that decides when you refetch, and a long-lived fallback you only read when the upstream fails. Your users see slightly old data instead of an error.

Store when the data was fetched next to the data, so the UI can say "rates as of 14:02" instead of passing old numbers off as current.

def exchange_rates():
    fresh = cache.get("rates:fresh")
    if fresh is not None:
        return fresh
    try:
        rates = {"data": fetch_rates(), "fetched_at": time.time()}
    except UpstreamError:
        stale = cache.get("rates:stale")
        if stale is None:
            raise                                 # nothing to fall back on
        return {**stale, "stale": True}           # show "as of fetched_at"
    cache.set("rates:fresh", rates, ttl=60)        # how often you want new data
    cache.set("rates:stale", rates, ttl=24 * 3600) # how old still beats an error
    return rates
record Rates(Map<String, Double> data, long fetchedAt, boolean stale) {}

    try {
        rates = new Rates(ratesClient.fetch(), System.currentTimeMillis(), false);
    } catch (UpstreamException e) {

        if (stale == null) throw e;                   // nothing to fall back on
        return new Rates(stale.data(), stale.fetchedAt(), true);
    }
    cache.set("rates:fresh", rates, Duration.ofMinutes(1));
    cache.set("rates:stale", rates, Duration.ofDays(1));
    return rates;
}
async function exchangeRates() {
  const fresh = cache.get("rates:fresh");

  let rates;
  try {
    rates = { data: await fetchRates(), fetchedAt: Date.now() };
  } catch (err) {
    const stale = cache.get("rates:stale");
    if (stale === undefined) throw err;           // nothing to fall back on
    return { ...stale, stale: true };             // show "as of fetchedAt"
  }
  cache.set("rates:fresh", rates, { ttl: 60 });
  cache.set("rates:stale", rates, { ttl: 24 * 3600 });
  return rates;
}

    Data      map[string]float64 `json:"data"`

}

    return r, nil
}

    }

Caveat. Only do this for data where an old answer is better than no answer. Exchange rates on a dashboard qualify. A balance, or a price you're about to charge, does not. During an outage every request still tries the upstream first, because the fresh copy is gone. If the upstream is slow to fail, also cache the failure for a few seconds and skip the call while it's there.

Rate limit

Count requests per client in a key named after the current time window. incr is atomic, so concurrent requests from many workers are all counted. When the window rolls over, the key name changes and counting starts again from zero.

incr creates a new counter with no TTL, so set one on the first increment. That way old windows clean themselves up.

def allow(client_id, limit=100, window=60):
    bucket = int(time.time() // window)
    key = f"rate:{client_id}:{bucket}"
    count = cache.incr(key)
    if count == 1:
        cache.expire(key, window * 2)   # old windows clean themselves up
    return count <= limit
boolean allow(String clientId, long limit, Duration window) {
    long bucket = Instant.now().getEpochSecond() / window.toSeconds();
    String key = "rate:" + clientId + ":" + bucket;
    long count = cache.incr(key);
    if (count == 1) {
        cache.expire(key, window.multipliedBy(2));  // old windows clean themselves up
    }
    return count <= limit;
}
function allow(clientId: string, limit = 100, windowSeconds = 60): boolean {
  const bucket = Math.floor(Date.now() / 1000 / windowSeconds);
  const key = `rate:${clientId}:${bucket}`;
  const count = Number(cache.incr(key));
  if (count === 1) {
    cache.expire(key, windowSeconds * 2);   // old windows clean themselves up
  }
  return count <= limit;
}
func allow(clientID string, limit int64, window time.Duration) (bool, error) {
    bucket := time.Now().Unix() / int64(window.Seconds())
    key := fmt.Sprintf("rate:%s:%d", clientID, bucket)
    count, err := cache.Incr(key, 1)
    if err != nil {
        return false, err
    }
    if count == 1 {
        cache.Expire(key, 2*window) // old windows clean themselves up
    }
    return count <= limit, nil
}
function allow(LyteCache $cache, string $clientId, int $limit = 100, int $window = 60): bool
{
    $bucket = intdiv(time(), $window);
    $key = "rate:{$clientId}:{$bucket}";
    $count = $cache->incr($key);
    if ($count === 1) {
        $cache->expire($key, $window * 2);   // old windows clean themselves up
    }
    return $count <= $limit;
}

Caveat. This is a fixed window. A client can send limit requests at the end of one window and limit more at the start of the next, so a burst of up to twice the limit gets through. If that matters, keep the last two windows and weight them, or use a token bucket. Also, if a process dies between incr and expire, that window's key never expires. The count stays correct, because the next window uses a new key, but the old row lingers until you delete it.

Idempotency keys

A client retries a payment because its connection dropped. Did the first attempt go through? An idempotency key answers that. The client sends the same key on every retry, and your handler makes sure the work runs once per key.

add() is the core of it. It writes the key only if it doesn't exist, as one atomic statement, and tells you whether it won. Two workers can receive the same retry at the same moment. Exactly one gets true and does the work. The other sees the claim and returns the first result, or a 409 if the first attempt is still running.

Store the outcome under the same key when you finish, so a later retry gets the original response rather than a second charge.

DAY = 24 * 3600

def charge(request_id, amount):
    key = f"idem:{request_id}"
    if not cache.add(key, {"status": "processing"}, ttl=DAY):
        previous = cache.get(key)
        if previous and previous["status"] == "done":
            return previous["receipt"]           # replay the first response
        raise Conflict("still processing")       # 409: tell the client to retry later
    try:
        receipt = payments.charge(amount, idempotency_key=request_id)
    except Exception:
        cache.delete(key)                        # failed: let a retry try again
        raise
    cache.set(key, {"status": "done", "receipt": receipt}, ttl=DAY)
    return receipt
record Claim(String status, Receipt receipt) {}

Receipt charge(String requestId, long amount) {
    String key = "idem:" + requestId;
    if (!cache.add(key, new Claim("processing", null), Duration.ofDays(1))) {
        Claim previous = cache.get(key, Claim.class);
        if (previous != null && previous.status().equals("done")) {
            return previous.receipt();               // replay the first response
        }
        throw new ConflictException("still processing");  // 409
    }
    Receipt receipt;
    try {
        receipt = payments.charge(amount, requestId);
    } catch (RuntimeException e) {
        cache.delete(key);                           // failed: let a retry try again
        throw e;
    }
    cache.set(key, new Claim("done", receipt), Duration.ofDays(1));
    return receipt;
}
const DAY = 24 * 3600;

async function charge(requestId: string, amount: number): Promise<Receipt> {
  const key = `idem:${requestId}`;
  if (!cache.add(key, { status: "processing" }, { ttl: DAY })) {
    const previous = cache.get<{ status: string; receipt?: Receipt }>(key);
    if (previous?.status === "done") return previous.receipt!; // replay
    throw new ConflictError("still processing");               // 409
  }
  let receipt: Receipt;
  try {
    receipt = await payments.charge(amount, { idempotencyKey: requestId });
  } catch (err) {
    cache.delete(key);                     // failed: let a retry try again
    throw err;
  }
  cache.set(key, { status: "done", receipt }, { ttl: DAY });
  return receipt;
}

    if err != nil {
        return nil, err

        if found, _ := cache.Get(key, &prev); found && prev.Status == "done" {

        }
        return nil, ErrStillProcessing // 409
    }
    receipt, err := payments.Charge(amount, requestID)
    if err != nil {
        cache.Delete(key) // failed: let a retry try again
        return nil, err
    }
    return receipt, cache.Set(key, claim{Status: "done", Receipt: receipt}, lytecache.TTL(24*time.Hour))
}
function charge(LyteCache $cache, string $requestId, int $amount): array
{
    $key = "idem:{$requestId}";
    $day = 24 * 3600;
    if (!$cache->add($key, ["status" => "processing"], ttl: $day)) {
        $previous = $cache->get($key);
        if (($previous["status"] ?? null) === "done") {
            return $previous["receipt"];              // replay the first response
        }
        throw new ConflictException("still processing");  // 409
    }
    try {
        $receipt = Payments::charge($amount, idempotencyKey: $requestId);
    } catch (Throwable $e) {
        $cache->delete($key);                         // failed: let a retry try again
        throw $e;
    }
    $cache->set($key, ["status" => "done", "receipt" => $receipt], ttl: $day);
    return $receipt;
}

Caveat. Three things to get right. First, the claim must not be evicted: an LRU eviction would let a duplicate through. We'd keep idempotency keys in their own namespace or file with eviction set to noeviction and no key cap. Second, the claim only stops your workers from starting the work twice. If a process dies after charging but before writing the result, the key stays at processing until it expires. That's why the examples also pass the request ID to the payment provider as its own idempotency key. Third, this only covers workers on one host. Across hosts, use a unique constraint in your database.

A cross-process lock

Use lock() when several workers on one machine share something that only one of them should touch at a time, such as a file, an external account, or a sync with another system. Each worker waits its turn.

"Run this job once" is a different problem. If five workers all fire the nightly export at midnight, a lock makes them run it one after another, five times. To run it once, claim the run itself with add(), using a key that names the run.

# One worker at a time:
with cache.lock("inventory-sync", timeout=120):
    sync_inventory()

# Once per day, however many workers fire at midnight:
today = datetime.date.today().isoformat()
if cache.add(f"job:nightly-export:{today}", os.getpid(), ttl=2 * 86400):
    run_export()
// One worker at a time:
try (CacheLock lock = cache.lock("inventory-sync", Duration.ofMinutes(2))) {
    syncInventory();
}

// Once per day, however many workers fire at midnight:
String today = LocalDate.now().toString();
if (cache.add("job:nightly-export:" + today, ProcessHandle.current().pid(), Duration.ofDays(2))) {
    runExport();
}
// One worker at a time:
{
  using lock = cache.lock("inventory-sync", { timeoutMs: 120_000 });
  syncInventory();
}

// Once per day, however many workers fire at midnight:
const today = new Date().toISOString().slice(0, 10);
if (cache.add(`job:nightly-export:${today}`, process.pid, { ttl: 2 * 86400 })) {
  runExport();
}
// One worker at a time:
lock, err := cache.Lock("inventory-sync", 2*time.Minute)
if err != nil {
    return err
}
syncInventory()
lock.Release()

// Once per day, however many workers fire at midnight:
today := time.Now().Format("2006-01-02")
if won, _ := cache.Add("job:nightly-export:"+today, os.Getpid(), lytecache.TTL(48*time.Hour)); won {
    runExport()
}
// One worker at a time:
$cache->lock("inventory-sync", timeout: 120.0)->block(function () {
    syncInventory();
});

// Once per day, however many workers fire at midnight:
$today = date("Y-m-d");
if ($cache->add("job:nightly-export:{$today}", getmypid(), ttl: 2 * 86400)) {
    runExport();
}

Caveat. Both only coordinate processes that share this cache file, which means one machine. The lock's timeout is also its TTL: if the work outlasts it, the lock expires and another worker can enter. The daily claim is never released, and that's deliberate, because the date in the key is what makes it once per day. If the export fails and you want a retry to run it, delete the claim in your error handler. (Python's lock() also accepts blocking=False to give up at once instead of waiting.)

Invalidate on write

When the data behind a cache entry changes, delete the entry so the next read fetches the new value. Do it after your database transaction commits, not before and not inside it.

Here's why the order matters. Delete first and a request that arrives before your commit misses, reads the old row from the database, and caches it again. That stale copy then stays until its TTL runs out. Delete after the commit and the next miss can only read the new row.

def rename_user(user_id, name):
    with db.transaction():
        db.execute("UPDATE users SET name = ? WHERE id = ?", (name, user_id))
    cache.delete(f"user:{user_id}")   # after the commit, never inside it
void renameUser(long userId, String name) {
    jdbc.inTransaction(tx -> tx.update("UPDATE users SET name = ? WHERE id = ?", name, userId));
    cache.delete("user:" + userId);   // after the commit, never inside it
}
async function renameUser(userId: number, name: string) {
  await db.transaction(async (tx) => {
    await tx.query("UPDATE users SET name = $1 WHERE id = $2", [name, userId]);
  });
  cache.delete(`user:${userId}`);    // after the commit, never inside it
}
func renameUser(ctx context.Context, userID int64, name string) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()
    if _, err := tx.ExecContext(ctx, "UPDATE users SET name = $1 WHERE id = $2", name, userID); err != nil {
        return err
    }
    if err := tx.Commit(); err != nil {
        return err
    }
    _, err = cache.Delete(fmt.Sprintf("user:%d", userID)) // after the commit
    return err
}
function renameUser(PDO $db, LyteCache $cache, int $userId, string $name): void
{
    $db->beginTransaction();
    $db->prepare("UPDATE users SET name = ? WHERE id = ?")->execute([$name, $userId]);
    $db->commit();
    $cache->delete("user:{$userId}");   // after the commit, never inside it
}

Caveat. A small race remains. A reader that loaded the old row just before your commit can write it into the cache just after your delete. That's rare, but it's why cached database rows should always carry a TTL as well: it caps how long a stale copy can survive. If other processes keep their own in-memory copies, deleting the shared entry isn't enough. Tell them, as in the next recipe.

Cross-worker invalidation with notify

This is the case the notification feature exists for. Several workers on one machine keep derived data in memory, such as a parsed config or a memo dict. When one worker changes the source, the others need to drop their copies. Deleting the shared cache entry doesn't reach their memory. An event does.

Publish after the commit, and run the listener on a background thread in each worker.

# the writer, after its transaction commits
cache.delete("pricing-rules")
cache.notify("invalidate", {"key": "pricing-rules"})

# every worker, at startup
def listen():
    with cache.watch("invalidate") as sub:
        for event in sub:
            local_memo.pop(event.payload["key"], None)

threading.Thread(target=listen, daemon=True).start()
// the writer, after its transaction commits
cache.delete("pricing-rules");
cache.notify("invalidate", Map.of("key", "pricing-rules"));

// every worker, at startup
Thread listener = new Thread(() -> {
    try (Subscription sub = cache.watch("invalidate")) {
        for (Event e : sub) {
            localMemo.remove(e.payload(Map.class).get("key"));
        }
    }
}, "lytecache-invalidate");
listener.setDaemon(true);
listener.start();
// the writer, after its transaction commits
cache.delete("pricing-rules");
cache.notify("invalidate", { key: "pricing-rules" });

// every worker, at startup
(async () => {
  using sub = cache.watch("invalidate");
  for await (const event of sub) localMemo.delete(event.payload.key);
})();
// the writer, after its transaction commits
cache.Delete("pricing-rules")
cache.Notify("invalidate", map[string]any{"key": "pricing-rules"})

// every worker, at startup
go func() {
    sub, err := cache.Watch([]string{"invalidate"})
    if err != nil {
        log.Fatal(err)
    }
    defer sub.Close()
    for ev := range sub.Events() {
        var p struct{ Key string `json:"key"` }
        if ev.Decode(&p) == nil {
            localMemo.Delete(p.Key) // a sync.Map: other goroutines read it
        }
    }
}()
// the writer, after its transaction commits
$cache->delete("pricing-rules");
$cache->notify("invalidate", ["key" => "pricing-rules"]);

// a long-running worker (queue worker, Octane, Swoole). PHP has no
// threads, so the worker polls inside this loop.

    unset($localMemo[$event->payload()["key"]]);
}

Caveat. Delivery is polled, so a worker drops its copy within about 50 ms, or up to about a second after a quiet spell. It's also at-least-once, so handlers must be safe to run twice (dropping a key twice is). It only reaches processes on this machine. A worker that starts after the event was published won't see it unless it resumes from a saved cursor, so a fresh worker should start with an empty memo. A plain PHP-FPM request starts empty anyway, so this matters for long-running PHP workers only.

Framework integration

Laravel has a real cache driver. The other frameworks below don't have an adapter yet, so these sections show how to wire the plain library in by hand. Each snippet is for one framework, so the language toggle doesn't apply to them.

Spring Boot

No adapter yet. There's no Spring CacheManager for lytecache, so @Cacheable won't use it. Register one LyteCache as a singleton bean and inject it. One instance per application is right. It's thread-safe, and each extra instance on the same file only adds connections and another sweeper thread.

Java 
@Configuration
public class CacheConfig {
    @Bean(destroyMethod = "close")
    public LyteCache lyteCache(@Value("${app.cache-path}") Path path) {
        return LyteCache.builder().path(path).namespace("orders").build();
    }
}

@Service
public class RatesService {
    private final LyteCache cache;
    private final RatesClient client;

    public RatesService(LyteCache cache, RatesClient client) {
        this.cache = cache;
        this.client = client;
    }

    public Rates rates(String base) {
        return cache.memoize("rates:" + base, Duration.ofMinutes(5), () -> client.fetch(base));
    }
}

destroyMethod = "close" stops the sweeper and flushes buffered state when the context shuts down. Set app.cache-path to a directory on a volume in production; see Troubleshooting for what happens if you don't.

Django

No adapter yet. There's no CACHES backend, so Django's own cache framework won't use lytecache. Create the cache in a module and import it where you need it.

Python 
# myproject/cache.py
from django.conf import settings
from lytecache import LyteCache

cache = LyteCache(settings.BASE_DIR / "var" / "cache.db", namespace="myproject")


# anywhere
from myproject.cache import cache

def product_view(request, pk):
    product = cache.get(f"product:{pk}")
    if product is None:
        product = serialize(Product.objects.get(pk=pk))
        cache.set(f"product:{pk}", product, ttl=600)
    return JsonResponse(product)

Create the cache in each worker, not before Gunicorn forks. The library opens its SQLite connection when you construct it and doesn't detect a fork(), so a cache built in the master process under --preload would hand every worker a copy of the same connection. Without --preload, each worker imports the module itself and gets its own.

Flask

No adapter yet. Attach one cache to the app and close it at exit.

Python 
import atexit
from flask import Flask, current_app
from lytecache import LyteCache

def create_app():
    app = Flask(__name__)
    app.extensions["lytecache"] = cache = LyteCache(app.instance_path + "/cache.db")
    atexit.register(cache.close)

    @app.get("/rates/<base>")
    def rates(base):
        cache = current_app.extensions["lytecache"]
        return cache.get(f"rates:{base}") or refresh_rates(base)

    return app

The same fork rule applies as for Django: build the cache inside create_app() in each worker, not at import time in a preloaded master.

Express

No adapter yet. Export one cache from a module, use it in routes or middleware, and close it on shutdown.

TypeScript

import { LyteCache } from "lytecache";

Guides

Troubleshooting

Find the symptom you're seeing. Each entry gives one way to confirm the cause, then the fix.

The habit that prevents most of these

Log the exact key at the place you write it and at the place you read it, and compare the two. Most "the cache doesn't work" reports turn out to be two different keys.

“My key is there when I write it and gone when I read it.”

Work down this list in order. The first check finds the problem most of the time.

  1. Compare the key strings character by character. Print them with quotes around them, at both sites. The usual culprit is something interpolated into the key: user:None or user:undefined because an ID wasn't loaded yet, 42 at one site and "42 " at the other, or a UUID in upper case in one place and lower case in another.
  2. Check the TTL right after the write. If ttl(key) prints 0.3 when you meant five minutes, the key really did expire. See the units entry at the end of this section.
  3. Check exists(key) at the read site. If it's false while the writer's own check is true, the two sites aren't looking at the same file or namespace. The next entry covers that.
Python 
print(repr(key), cache.ttl(key))       # at the write site, straight after set()
print(repr(key), cache.exists(key))    # at the read site

“stats shows zero keys, but my app is definitely caching.”

Almost always a namespace mismatch. Your app opened the cache with a namespace, and the CLI looks in default unless you tell it otherwise. Both are reading the right file, just different partitions of it. Nothing errors. The CLI just sees an empty namespace, which makes this the most confusing failure in the product.

Look at how your app opens the cache, then pass the same namespace to the CLI:

In your appOn the command line
LyteCache(namespace="sessions")lytecache --namespace sessions stats
.namespace("sessions") (Java)
new LyteCache({ namespace: "sessions" })
lytecache.WithNamespace("sessions")
new LyteCache(namespace: "sessions")

To see every namespace in a file and how many keys each holds, open it in the Admin UI, whose sidebar lists them with counts. Or ask SQLite directly:

Terminal 
sqlite3 "$(lytecache which | head -1)" "SELECT namespace, COUNT(*) FROM cache GROUP BY namespace"

Two more things that look like this problem but aren't. A LYTECACHE_NAMESPACE environment variable does nothing, because no implementation reads one; set the namespace in code. And the hits and misses lines in lytecache stats always read 0. They count the CLI's own reads, not your app's. The line that tells you whether you're looking at the right namespace is keys.

“The cache is empty after every deploy or restart.”

The file is living in the container's writable layer, which is thrown away whenever the container is recreated. Confirm it by looking for a volume at the cache path: if docker inspect shows nothing mounted there, that's the cause.

Mount a named volume on the cache directory and point LYTECACHE_PATH into it:

docker-compose.yml 
services:
  app:
    environment:
      LYTECACHE_PATH: /var/cache/lytecache/app.db
    volumes:
      - lytecache-data:/var/cache/lytecache

volumes:
  lytecache-data:

Mount the directory, not the .db file, because SQLite creates app.db-wal and app.db-shm next to it.

“SQLITE_CANTOPEN / unable to open database file”

The cache directory doesn't exist, or it exists but is owned by root while your app runs as a non-root user. Confirm it from inside the container with ls -ld /var/cache/lytecache and id.

Create the directory and hand it to your app's user in the Dockerfile, before the USER line:

Dockerfile 
RUN mkdir -p /var/cache/lytecache && chown app:app /var/cache/lytecache
USER app

When Docker mounts an empty named volume for the first time, it copies that directory's ownership from the image. So getting it right in the image fixes the volume too. A volume that was already created with root ownership keeps it, though. Fix that one with a one-off chown, or remove the volume and let it be recreated.

“The CLI says the database file doesn't exist, and Docker logs Volume … Created.”

You're running the CLI in a different Compose project from your app. Compose names volumes after the project (myapp_lytecache-data), and it takes the project name from the directory you run it in unless something sets it explicitly. Run the CLI service from another directory and Compose looks for otherdir_lytecache-data, doesn't find it, and creates a new, empty one.

Compose creating a volume or network when you only meant to run the CLI is the tell. It means you're not in the app's project. Check which projects exist and run the CLI in the right one:

Terminal 
docker compose ls                                     # the real project names
docker compose -p myapp run --rm lytecache-cli stats  # run inside the app's project
docker volume rm otherdir_lytecache-data               # tidy up the stray volume

“The Admin UI starts, but the dashboard is empty.”

The UI container mounts a different volume from the one your app writes to. The container starts fine either way, so nothing tells you. Compare the mounts of the two containers:

Terminal 
docker inspect myapp-app-1 --format '{{range .Mounts}}{{.Name}} -> {{.Destination}}{{println}}{{end}}'
docker inspect myapp-lytecache-ui-1 --format '{{range .Mounts}}{{.Name}} -> {{.Destination}}{{println}}{{end}}'

The volume names must match. If they don't, mount the app's volume in the UI service. Multiple app services, one Admin UI covers setups with several services.

“Writes seem to be getting lost under load.”

SQLite allows one writer at a time. A process that finds the file locked waits up to five seconds (busy_timeout=5000) for its turn. If it still can't write, it gets a "database is locked" error. It doesn't silently drop the write. So a lost write means either an error that something swallowed, or a bug.

Look for a try or catch around cache writes that discards the error. While you investigate, turn on strict mode too: by default a failing read is logged and returned as a miss, which can look like a write that never happened. Read-modify-write code (get, change, set) loses updates whenever two writers overlap. Use incr, the hash operations or lock() instead.

If you've ruled those out, please open an issue and include the library and version (pip show lytecache, npm ls lytecache, the Maven/Composer version or the Go module version), the SQLite version, how many processes write concurrently, and whether the file sits on a network filesystem. NFS and Kubernetes ReadWriteMany volumes aren't supported, because SQLite's locking doesn't work reliably on them.

“My keys expire sooner or later than I expected.”

In Python, Node.js and PHP, ttl is in seconds. Passing milliseconds out of habit, like ttl=5000, gives you 83 minutes instead of 5 seconds. Going the other way, ttl=0.3 is 300 milliseconds. Java and Go take a typed duration, so they can't get this wrong.

Check what you actually stored straight after the write:

Python 
cache.set("otp:42", code, ttl=5000)
cache.ttl("otp:42")    # 4999.9 -> you meant ttl=5

If the TTL is right but the row is still in the file after it expired, that's the sweep interval. Reads already treat it as gone; see Lazy and active expiration.

Guides

TTL & expiration

TTLs work the same way for every value type: strings, numbers, dataclasses, dicts, POJOs, records. Storing an object changes nothing.

Watch the units

Python's, Node.js's, and PHP's ttl are all plain numbers, in seconds (a float in Python and PHP, a number in Node). ttl=5000 / { ttl: 5000 } means "expire in 5000 seconds" (~83 minutes), not 5 seconds. That's the most common reason a key seems to "never expire." Java's and Go's are explicit (a Java Duration, a Go time.Duration), so there's no unit ambiguity there.

cache.set("session", {"user_id": 42}, ttl=300)   # expires in 300s (5 min)
cache.set("otp", "123456", ttl=0.5)              # expires in 500ms

cache.ttl("session")        # seconds remaining, e.g. 298.7
cache.ttl("permanent_key")  # -1 if no TTL was set
cache.ttl("missing")        # None if the key doesn't exist

cache.expire("session", 60)   # overwrite the TTL: now expires in 60s
cache.persist("session")      # remove the TTL entirely
cache.touch("session", 300)   # sliding expiration: refresh back to 300s

cache.set("session", "42", Duration.ofMinutes(5));
cache.set("otp", "123456", Duration.ofMillis(500));

cache.ttl("session");     // Duration remaining
cache.ttl("permanent");   // Duration.ofSeconds(-1) if no TTL
cache.ttl("missing");     // null if the key doesn't exist

cache.expire("session", Duration.ofSeconds(60));  // overwrite the TTL
cache.persist("session");                          // remove the TTL entirely
cache.touch("session", Duration.ofMinutes(5));     // sliding expiration
cache.set("session", { userId: 42 }, { ttl: 300 });  // expires in 300s (5 min)
cache.set("otp", "123456", { ttl: 0.5 });            // expires in 500ms

cache.ttl("session");        // seconds remaining, e.g. 298.7
cache.ttl("permanentKey");   // -1 if no TTL was set
cache.ttl("missing");        // undefined if the key doesn't exist

cache.expire("session", 60);   // overwrite the TTL: now expires in 60s
cache.persist("session");      // remove the TTL entirely
cache.touch("session", 300);   // sliding expiration: refresh back to 300s
cache.Set("session", 42, lytecache.TTL(5*time.Minute))   // expires in 5 min
cache.Set("otp", "123456", lytecache.TTL(500*time.Millisecond))

_, hasExpiry, found, _ := cache.TTLOf("session")   // remaining time.Duration

Lazy and active expiration

Every implementation expires keys in two ways:

  • Lazily, on every read (get / exists / getAll / getMany / TTLOf): the read treats an expired row as a miss and deletes it on the spot, even with the background sweeper disabled.
  • Actively, by a background sweeper (a thread in Python/Java, a setInterval timer in Node.js, a goroutine in Go) that runs every sweep_interval / sweepInterval / WithSweepInterval (default 60s). It deletes expired rows in batches, so dead keys don't hold disk space even if nothing reads them again. PHP has no background threads. Instead it runs short maintenance passes opportunistically (roughly every 100 operations, throttled by sweepInterval). In a Laravel app, also schedule the lytecache:maintain artisan command so a quiet cache still gets swept.

Open the file in a SQLite browser right after a key expires and you may still see the row. The sweeper hasn't reached it yet. get() and exists() already treat it as gone. To remove expired rows right away, lower the sweep interval or run lytecache maintain (Maintain() in Go, maintain() in PHP). To shrink the file afterwards, call vacuum().

Namespaces

Two LyteCache instances on the same file but different namespaces are fully isolated. flush() on one never touches the other's keys. That's the usual reason flush() seems not to delete everything: you're flushing a different namespace from the one you wrote to.

Distributed locks

Locks are built on the same atomic add() as everything else, so only one holder can have a given lock name at a time, across threads and processes on this host. The timeout does two jobs. It's how long lock() waits to acquire, and it's the lock's own TTL, so a holder that crashes can't wedge the lock forever. Pick a timeout longer than the work takes: if the work runs past it, the lock expires and another worker can take it.

    do_critical_work()
try (CacheLock lock = cache.lock("resource", Duration.ofSeconds(30))) {
    doCriticalWork();
}

defer lock.Release()
doCriticalWork()

    doCriticalWork();

Local events (notify / watch)

Read this first

Notifications work between processes on one machine. A process writes an event, and other processes polling the same file pick it up. Nothing crosses a machine boundary: if your subscribers run on different hosts, you need Redis or a message broker. Delivery takes about one poll interval (50 ms, or up to about 1 s after an idle spell). It's at-least-once, so make your handlers idempotent. This is not Redis Pub/Sub. Events are rows with a monotonic seq, kept for an hour by default, so a restarted subscriber picks up where it left off.

The main use is cross-worker cache invalidation:

} catch (GapException $err) {                          // events past retention are gone
    resync();
    $cache->saveCursor("worker-b", $err->resumeSeq);   // accept the loss explicitly
}

Retention (event_retention, default 1 hour, plus an optional count cap) sets how long a subscriber can be down without losing events. If you never call notify or watch, no events table is created and no polling thread starts. The full guide, latency numbers and the comparison with Redis are in docs/notifications.md.

Change listeners

There are two ways to react to changes in the cache. onChange (on_change) works in-process. It's immediate and doesn't touch SQLite. Listeners run only after the write commits, so a rolled-back setMany notifies nobody, and a listener that throws never fails the write. publishChanges works across processes. It writes each matching mutation to the reserved __cache__ channel, so it's polled and costs one event row per call. Either way, a bulk write produces one record, not one per key. Past 100 keys the key list is dropped and truncated is set.

def drop(rec):                       # a ChangeRecord: op, namespace, keys, count, truncated
    if rec.truncated:
        memo.clear()                 # a bulk change: refetch by namespace or prefix
    else:
        for key in rec.keys:
            memo.pop(key, None)

unsubscribe = cache.on_change(drop, events={"set", "delete", "flush"})
cache.set_many(rows)                 # 1,000 keys -> ONE record: count=1000, truncated=True

# cross-process alternative: also publish deletes/flushes to "__cache__"
cache = LyteCache(publish_changes={"delete", "flush"})
Runnable unsubscribe = cache.onChange(rec -> {
    if (rec.truncated()) {
        memo.clear();                // a bulk change: refetch by namespace or prefix
    } else {
        rec.keys().forEach(memo::remove);
    }
}, EnumSet.of(ChangeOp.SET, ChangeOp.DELETE, ChangeOp.FLUSH));

// cross-process alternative: also publish deletes/flushes to "__cache__"
LyteCache cache = LyteCache.builder().publishChanges(ChangeOp.DELETE, ChangeOp.FLUSH).build();
const unsubscribe = cache.onChange((rec) => {
  if (rec.truncated) memo.clear();   // a bulk change: refetch by namespace or prefix
  else for (const key of rec.keys!) memo.delete(key);
}, { events: ["set", "delete", "flush"] });

// cross-process alternative: also publish deletes/flushes to "__cache__"
const cache = new LyteCache({ publishChanges: ["delete", "flush"] });
unsubscribe, err := cache.OnChange(func(rec lytecache.ChangeRecord) {
    if rec.Truncated {

        return
    }
    for _, k := range rec.Keys {

    }
}, lytecache.OpSet, lytecache.OpDelete, lytecache.OpFlush)

Storage spec & type codes

Every implementation reads and writes the same schema: one SQLite file in WAL mode, with PRAGMA busy_timeout=5000 so a process that finds the file locked waits instead of failing. Every value carries a value_type code:

Code Type Encoding
0 Bytes Raw bytes, stored as-is
1 String UTF-8 text
2 Integer UTF-8 decimal text, not binary. That's what lets incr/decr be one atomic SQL UPSERT in every language.
3 Float UTF-8 decimal text, same reasoning as integers
4 JSON Any object, dict, list, dataclass, POJO, record, JS object, Go struct/map/slice, or PHP array/object/enum
5 Python pickle Python-only escape hatch; reading it from Java, Node.js, Go, or PHP raises a clear error instead of returning garbage
6 Java serialized Reserved, never written; reading it from Python, Node.js, Go, or PHP raises a clear error

Node.js has a single number type rather than Python's int/float or Java's long/double, so its implementation picks type code 2 vs. 3 by shape (Number.isInteger()) rather than by caller intent, using bigint for integers beyond Number.MAX_SAFE_INTEGER. See lytecache-node/SPEC.md for the full rules.

Go, like Python and Java, has distinct integer and floating-point types, so it decides type codes by the value's actual Go type rather than by shape: any Go integer type stores as code 2, float32/float64 as code 3. A uint64 beyond what signed 64-bit integers can hold is rejected outright rather than silently truncated. See lytecache-go/SPEC.md for the full rules.

PHP strings are ambiguous between "raw bytes" and "text," unlike the other languages' distinct byte-array types, so lytecache uses a Bytes wrapper class to mean code 0 explicitly. A plain PHP string always stores as code 1. Objects serialize via JsonSerializable when implemented, else their public properties; a DateTimeInterface serializes to an RFC 3339 string and a BackedEnum to its backing value, matching the conventions above. See lytecache-php/SPEC.md for the full rules.

The zero-config default path derivation (<project-id> = SHA-256 of the resolved working directory) is byte-for-byte identical across every implementation, so all of them land on the same file for the same project directory. See Where is my data? above.

Docker

The CLI is also published as a multi-arch container image (linux/amd64, linux/arm64). It's about 7 MB, built on scratch with nothing in it but the static binary, so you can inspect a cache file without installing anything. lytecache has no server mode: a CLI container runs one command and exits. (The Admin UI does serve a web page, but it isn't a cache server either.)

Mount the same volume your application uses at /var/cache/lytecache and set LYTECACHE_PATH to the value the app already uses, and the CLI needs no --db flag. It reads that variable exactly the way every library on this page does:

Terminal 
docker run --rm -v myapp-cache:/var/cache/lytecache \
  -e LYTECACHE_PATH=/var/cache/lytecache/cache.db \
  ghcr.io/lytecache/lytecache:latest stats

With Compose, add a service like this next to your app. It uses the same LYTECACHE_PATH and mounts the same named volume, which is why it needs no --db:

Dockerfile

Tools

Admin UI

A local web console for the same database files the CLI reads, like RedisInsight or pgAdmin. It isn't a cache server: it speaks no cache protocol and no application connects to it. It's lytecache-go's public API with a browser on top, started with lytecache ui --port 7070.

It ships in the same binary as the CLI, so there's nothing extra to install. If you haven't installed lytecache yet, see Install in the CLI section, or jump straight to Docker below if you'd rather not install anything locally at all.

Fleet dashboard

Every configured database side by side, with a health flag when usage nears a cap, expired keys pile up, or a subscriber loses events.

Delete-only, on purpose

The UI can delete data. It cannot create or change it. There's no route that accepts a new or edited value, so even a hand-crafted request has nothing to reach.

Events tab

A live tail of each database's notify events, retention stats, and lag for every subscriber cursor. It can't publish events. With --allow-delete it can purge them.

Prometheus /metrics

Per-database gauges for keys, size, evictions, expired-present, events and subscriber lag. A scrape never writes to the file.

Runs in the background

lytecache service install registers it with launchd, systemd or the Windows Service Control Manager, so it survives logout and starts on boot.

Install and run it, step by step

  1. Install lytecache

    The CLI and the Admin UI are one binary, so this one install covers both.

    Terminal 
    brew install lytecache/tap/lytecache

    On Linux/Windows/from source, or want the Docker image instead? See Install in the CLI section above.

  2. Point it at a database (optional)

    If you know the path, name it with --db. If you don't, skip this step. With no flags at all, the UI scans the standard cache locations for you (details below).

  3. Run it

    Start it in the foreground first. Ctrl+C stops it, and nothing is left running:

    Terminal 
    lytecache ui

    To keep it running across logouts and reboots, install it as a background service.

  4. Open it and log in

    Visit http://127.0.0.1:7070 and log in with admin/admin. You land on the fleet dashboard.

  5. Change the password before exposing it anywhere

    This only matters if you'll reach the UI from beyond 127.0.0.1, and there it's enforced: the UI refuses to bind anywhere else while the password is still admin. Run lytecache ui passwd to change it.

Quickstart

Open http://127.0.0.1:7070, log in with admin/admin, and you're at the fleet dashboard. Passing --allow-delete turns on delete/flush/maintain; without it, those routes return 403 whether or not the browser shows a button for them.

With no --db, --scan or config file, lytecache ui scans two standard locations. One is <platform cache dir>/lytecache, where the library puts files when your app doesn't set a path. The other is /var/cache/lytecache, the volume-mount convention used in the Docker examples. So the same zero-flag start works on a laptop and in a container. Configure any database explicitly and the scan is skipped.

Using it

Click a database row to open its key browser. The sidebar lists every namespace with its key count. A mismatched namespace is the most common reason a key seems to be missing, and this makes it hard to overlook. Click a key to open the value viewer. JSON is pretty-printed and collapsible, and every value stays hidden until you click "Reveal value". With --allow-delete you also get a delete button, bulk delete, and a flush-namespace control that makes you type the namespace name, so a stray click can't wipe anything.

/ focuses the search box from anywhere (it searches every configured database, not just the one you're in); arrow keys move through a key list, Esc clears the current selection or search.

Guardrails you can't switch off

The UI refuses to bind anything other than 127.0.0.1 while the password is still admin. If someone reaches it from another machine after the password was reset to the default, it forces a password change before showing anything else. No flag turns either check off. To reach a remote instance, we'd use an SSH tunnel (ssh -L 7070:localhost:7070 you@host) rather than expose the port at all.

Docker

The image includes the ui subcommand. Inside the container, bind 0.0.0.0: Docker can't forward a published port to a listener that only accepts loopback. Then restrict it to 127.0.0.1 on the host side:

Terminal 
docker run --rm -p 127.0.0.1:7070:7070 \
  -v myapp-cache:/var/cache/lytecache \
  -v lytecache-ui-config:/home/lytecache/.config/lytecache \
  -e LYTECACHE_UI_PASSWORD=change-me \
  ghcr.io/lytecache/lytecache:latest \
  ui --host 0.0.0.0 --insecure --no-metrics --db orders=/var/cache/lytecache/orders.db

Mount the config volume as well as the cache volume. ui.yaml holds the credentials and the session secret. If it isn't on a volume, the password goes back to admin/admin every time the container is recreated.

With Compose, add it as a profiled service next to your app. As with the CLI service above, using the app's LYTECACHE_PATH and volume is what makes --db unnecessary:

  # ... your existing app service ...

  lytecache-ui:
    image: ghcr.io/lytecache/lytecache:latest

    command: ["ui", "--host", "0.0.0.0", "--port", "7070", "--allow-delete", "--insecure", "--no-metrics"]

Pulling a newer image

Docker doesn't fetch a newer :latest on its own. If the image is already on your machine, docker compose up keeps using it. Two ways to get the new one:

Terminal 
# pull, then recreate the container so it actually uses what was just pulled
docker compose pull lytecache-ui
docker compose up -d --force-recreate lytecache-ui

# or do both in one command
docker compose up -d --pull always lytecache-ui

To make that the default, add pull_policy: always to the service, as the snippet above does. Then a plain docker compose up -d lytecache-ui checks for a newer :latest first.

Multiple app services, one Admin UI

This is the most common setup mistake. lytecache-ui has to mount the same volumes your app services write to. Point it at a leftover or unrelated volume and the container still starts. It just shows an empty dashboard, because it's looking somewhere your app isn't.

Two patterns handle this correctly, trading a bit of setup for a bit of isolation:

✓ One shared volume, one file per service

  • Each service gets its own LYTECACHE_PATH filename (admin.db, pos.db, ...) but mounts the same volume
  • lytecache-ui mounts that one volume and uses --scan, so adding a service needs no change to lytecache-ui
  • The setup we recommend for most fleets

✕ One shared file for everything

  • Every service's writes queue behind every other service's. SQLite has one writer at a time and can't tell which callers are unrelated.
  • One corrupted/locked file takes down cache access for your whole fleet at once, not just the service that caused it
  • Collapses the dashboard to one row instead of one per service
  • Not recommended unless you've implemented per-service namespace isolation in application code (see below) and accept the write-contention trade-off

A third option also works: a separate volume per service. Mount each one into lytecache-ui at its own subdirectory and use repeatable --db name=path flags instead of --scan. Each new service needs more wiring, but a lock or corruption problem in one file can't touch the others.

Running as a background service

Installed via Homebrew?

Homebrew already ran service install for you when brew install or brew upgrade finished. It only registers the service, so nothing is listening until you start it. Go straight to lytecache service start below.

Terminal 
lytecache service install --db orders=/data/orders.db --allow-delete
lytecache service start
lytecache service status

service install accepts every flag lytecache ui does and saves them, so the service starts the same way every time. It installs a user LaunchAgent on macOS and a user systemd unit on Linux (--system for a system-wide unit). On Windows it uses the Service Control Manager from an elevated shell, and a Scheduled Task at logon otherwise. To change the flags, for example to add a --db, run service install again. You don't need to uninstall first.
